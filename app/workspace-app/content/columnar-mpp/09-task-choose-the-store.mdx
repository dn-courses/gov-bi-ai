The same readings live in two stores. Eight workloads ask for them, each with its own query and its
own number of runs a month. For each one you choose where the data lives and how it is laid out,
build it, measure it, and write down three numbers. One is solved for you. At the end you choose for
all eight at once.

## How each workload goes

Every workload shows its query, then two cells and two buttons.

- **The PostgreSQL cell** is plain SQL: the index you choose. Start its name with `ho_`.
- **The BigQuery cell** builds your own copy of the table, laid out as you choose. Name the table
  after the workload (`w4`) and the shared table simply `lab_station_status`: `bq(...)` puts the
  table in your own dataset, runs the statement, and prints what building it took. A copy must
  **name its columns**: `SELECT *` would bill the whole table, and anything above 5 GB is refused.
- **The two buttons** run the workload's query, exactly as shown, and give three numbers. On
  BigQuery the query runs on your table for that workload when you have built it, and on the shared
  table when you have not. Press them before you build anything, and again after.

The three numbers:

- **data read.** On BigQuery, the bytes billed. On PostgreSQL, every page of 8 kB the query visits,
  in memory or on disk: a page visited twice counts twice, so an index can report more than the
  whole table.
- **latency.** On PostgreSQL the median of three runs, in a transaction that is rolled back; on
  BigQuery one run, which varies from run to run.
- **cost.** On PostgreSQL the server's rent, the same for one run or a million. On BigQuery the
  price of one run, times the workload's runs a month.

## Solved: W3 · One system, hour by hour, one day · 4,400 runs a month

A dashboard tile: 50 viewers open it 4 times a working day.

```text
-- PostgreSQL
SELECT date_trunc('hour', captured_at) AS hour, avg(bikes_available) AS bikes
FROM station_status
WHERE system_id = 'NYC' AND captured_at >= '2026-08-15' AND captured_at < '2026-08-16'
GROUP BY 1 ORDER BY 1

-- BigQuery
SELECT TIMESTAMP_TRUNC(captured_at, HOUR) AS hour, AVG(bikes_available) AS bikes
FROM lab_station_status
WHERE system_id = 'NYC' AND captured_at >= '2026-08-15' AND captured_at < '2026-08-16'
GROUP BY hour ORDER BY hour
```

On PostgreSQL, an index that starts with the day and then the system:

```sql id=w3-pg
DROP INDEX IF EXISTS ho_w3;
CREATE INDEX ho_w3 ON station_status (captured_at, system_id);
```

On BigQuery, a copy partitioned by day:

```python id=w3-bq standalone
bq("""
CREATE OR REPLACE TABLE w3
PARTITION BY DATE(captured_at)
AS SELECT station_id, system_id, captured_at, bikes_available, docks_available
FROM lab_station_status
""")
```

The query asks for one day of one system, so both structures put a day's rows in one place: one
range of the index, one partition of the table, and the rest is never read. BigQuery wins on price
and PostgreSQL on latency, and neither reads more than a few megabytes.

Points for the room:

- **The 10 MB floor.** Every good BigQuery layout lands on 10 MB a run; for W1's 100,000 runs that is
  still $5.96–7.15 a month, for a question PostgreSQL answers from 5 pages, 25,000 times faster.
- **One layout does not serve all.** Day partitions are right for W3 and wrong for W1 and W4: a day
  is about 10 MB, so clustering inside it has nothing left to skip. Two copies at $0.0054 each beat a
  compromise.
- **No index helps W5**, and a covering index makes it slower: its page visits add up to more than
  the table (31 GB of visits through a 1 GB index). Only adding up in advance goes under 507 MB.
- **Fewer columns in a copy change nothing for a query**: BigQuery reads only the columns asked for
  anyway. They make the copy cheaper to build (903 MB billed instead of a refused 6.33 GB).
- **An UPDATE on BigQuery takes seconds**, even when it bills 10 MB.
- **At real volume the server cannot keep up**: 4,400 W6 weeks a month × 98 s is 120 hours of one
  disk, and the whole-capture form is 29 minutes a run. On BigQuery, the same 4,400 runs over the
  whole capture would cost $1,153 a month: a summary table brings that back to cents.
- **All eight on BigQuery**: about $103 a month, every answer in about 2 s at most (W2 up to 5 s).
  The split the key arrives at: W1 and W2 on PostgreSQL, W5 to W8 on BigQuery, W3 and W4 on either.

</details>
